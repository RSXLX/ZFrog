# ZFrog 桌面端问题总结、用户痛点与详细开发计划

## 一、文档目标

基于当前 `desktop-pet/` 真实实现，对桌面端进行一次面向产品落地的收敛：

1. 总结现阶段最关键的问题。
2. 将问题翻译成用户真实痛点。
3. 给出可排期、可分阶段执行的开发计划。
4. 给出现有技术栈可承接的动画生成方案。

本文档不讨论“大而全重构”，只讨论能让桌面端更可玩、更稳定、更像一个桌宠产品的最短路径。

---

## 二、当前结论

当前桌面端更接近：

**一个功能很多、视觉上已经有桌宠雏形、但完成度不均衡的高保真原型。**

它的优点是：

1. 功能面广，`任务 / 好友 / 勋章 / 旅行 / 家园 / 背包 / 设置 / 链上监控 / 资料 / 安静模式` 都有壳。
2. Electron 桌宠形态已经成立，透明窗口、拖拽、悬浮、菜单都可运行。
3. 旅行弹层、状态展示、设置登录等模块已经不是纯静态图，而是带真实业务意图。

它的核心问题是：

1. 功能完成度差异过大。
2. UI 风格不统一。
3. 在线与离线边界不清晰。
4. 用户主循环不清晰。
5. 动画很多，但缺少统一的动作语言和生产管线。

因此当前桌面端最需要的不是继续堆功能，而是：

**先把“可稳定试玩 + 主循环明确 + 体验统一 + 动画语言成型”这四件事做扎实。**

---

## 三、问题总结

## 3.1 产品层问题

1. 主玩法不聚焦。
   用户打开桌宠后，能看到很多入口，但不知道第一步该做什么、什么最重要、什么会带来成长反馈。
2. 桌宠人格存在感不稳定。
   目前更像一个“功能入口容器”，而不是一个会陪伴、会表达情绪、会引导用户的宠物角色。
3. 桌面端定位不够明确。
   它究竟是：
   1. Web 的伴随入口
   2. 独立可玩的轻养成产品
   3. 链上监控助手

   当前实现里三者都沾一点，导致体验目标分散。

## 3.2 功能层问题

1. 在线能力依赖后端，但默认异常态不可用。
   默认 API 基址为 `http://localhost:3001/api`，后端未启动时，通知、我的青蛙、旅行历史、旅行统计都会报错。
2. 本地状态与远端状态混用，但用户看不出来区别。
   例如旅行弹层会优先拉远端数据，失败后回退到本地数据；这个策略对工程是合理的，但对用户几乎不可见。
3. 部分面板接近静态展示。
   好友、部分收集/资料类能力更多是“展示卡片”，缺乏下一步动作。
4. 登录链路偏开发者视角。
   设置页当前是“钱包地址 -> nonce -> 外部签名 -> 粘贴签名 -> 换 token”，可理解，但不够像普通用户产品。

## 3.3 UI 层问题

1. 视觉语言不统一。
   主桌宠是轻量悬浮风，旅行面板是高完成度卡片风，其余不少弹层仍是基础白底表单风。
2. 大量内联样式导致复用困难。
   容易造成颜色、圆角、间距、按钮层级在不同弹层间持续漂移。
3. 缺少统一的桌宠品牌识别。
   目前还没有形成“这是 ZFrog 桌宠”的独特界面语言。

## 3.4 交互层问题

1. 反馈链不完整。
   点击后能打开功能，但不总能得到“这次行为对成长有什么影响”的反馈。
2. 异常状态没有产品化表达。
   API 不可达、未登录、未绑定青蛙、同步失败这些状态主要停留在控制台，不在界面上解释。
3. 悬浮桌宠与弹层式大面板的切换逻辑还不够顺。
   当前体验像是“小桌宠壳 + 一组常规弹窗”，还没有形成统一的动线。

## 3.5 动画层问题

1. 已有不少 Framer Motion 动作，但更多是“点状动画”，不是状态机。
2. 现有 `lottie-react` 仍处于占位状态，`FrogLottie.tsx` 还是 placeholder 数据。
3. 缺少动作分层：
   1. 基础待机
   2. 情绪反应
   3. 行为动作
   4. 特效反馈
4. 缺少统一的动画资产生产方式，后续一旦扩动作，维护成本会迅速上升。

---

## 四、用户痛点

把上面的问题换成用户语言，核心痛点是 8 个：

1. 我打开后不知道先玩什么。
2. 我点了一些功能，但不知道它和“养成我的蛙”有什么关系。
3. 有的页面像真功能，有的页面像占位演示，体验不稳定。
4. 网络或后端不通时，产品不会清楚告诉我发生了什么。
5. 登录和绑定流程太技术化，不像普通玩家产品。
6. 桌宠会动，但情绪和动作还没有形成强记忆点。
7. 弹层很多，但视觉风格不统一，像几个版本的 UI 拼在一起。
8. 我感觉它功能很多，但不够“想继续回来养”。

如果不解决这些痛点，桌面端会卡在一个很典型的阶段：

**能展示、能演示、能解释，但留不住用户。**

---

## 五、产品目标重定义

桌面端下一阶段的目标应该定义成：

**把 ZFrog 桌面端从“功能总装机”收敛成“离线可玩、在线增益、主循环清晰、人格鲜明的轻陪伴桌宠”。**

具体要达成 4 个结果：

1. 用户第一次打开后，3 分钟内能完成一次完整互动闭环。
2. 即使后端不可用，桌宠也能正常玩基础养成。
3. 用户能明确感知“这只蛙现在是什么心情、为什么这样、我做什么会改变它”。
4. 在线能力成为增强项，而不是基础可玩性的前置条件。

## 六、详细开发计划

## 6.1 总体原则

1. 先稳住可玩性，再扩在线能力。
2. 先统一主循环，再扩功能入口。
3. 先定义动画语言，再扩动作数量。
4. 先建立组件与样式规范，再做大面积 UI 润色。

## 6.2 阶段划分

建议拆成 4 个阶段，约 6 到 8 周。

### Phase A：稳定可玩基线（Week 1-2）

目标：
把桌面端变成“离线就能玩、在线时更好玩”的产品，而不是“缺后端就半瘫痪”的产品。

交付项：

1. 建立桌面端运行模式
   1. `offline-demo`
   2. `local-online`
   3. `production-online`
2. 给所有远端依赖增加统一状态层
   1. 未连接
   2. 同步中
   3. 已同步
   4. 降级到本地数据
3. 把通知、旅行历史、我的青蛙、议会提醒的异常态产品化。
4. 去掉默认假钱包给人的误导感，改成显式“未登录试玩模式”。
5. 为离线模式准备最小种子数据。

验收标准：

1. 不启动后端时，桌宠主界面、喂养、互动、旅行、本地背包、本地任务都可正常运行。
2. 所有在线功能失败时，界面上都有清晰说明，不再只在控制台报错。
3. 用户可以明确知道自己当前是试玩模式还是已登录联机模式。

### Phase B：主循环与信息架构收敛（Week 2-4）

目标：
让用户知道“打开桌宠后该做什么”，并压缩无效入口。

交付项：

1. 定义桌宠核心日循环：
   `看状态 -> 互动/喂养 -> 做 1 个今日动作 -> 收到反馈`
2. 重做主界面信息优先级
   1. 当前情绪
   2. 关键状态
   3. 今日任务
   4. 一个推荐动作
3. 收敛菜单入口层级
   1. 一级：互动、旅行、任务、背包
   2. 二级：好友、图鉴、资料、设置
   3. 实验入口：链上监控、开发特性
4. 给每个动作补“结果反馈”
   1. 数值变化
   2. 情绪变化
   3. 经验/奖励变化
   4. 记忆/关系变化
5. 把“好友/家园/收集/资料”改成可执行动线，而不是只有信息展示。

验收标准：

1. 新用户第一次打开后，不看说明也能完成一次完整养成循环。
2. 菜单入口数量和优先级更清晰。
3. 每个核心动作都能给出至少一种成长反馈。

### Phase C：UI 统一与桌宠人格强化（Week 4-6）

目标：
让它看起来像一个产品，而不是几个模块拼起来的 Demo。

交付项：

1. 建立桌面端设计 token
   1. 颜色
   2. 圆角
   3. 阴影
   4. 间距
   5. 字号
2. 重构弹层规范
   1. 小弹层：信息/确认
   2. 中弹层：任务/背包/好友
   3. 大弹层：旅行/家园/资料
3. 统一按钮和状态标签样式。
4. 提升桌宠人格表达
   1. 问候语分时段
   2. 情绪台词库
   3. 行为反馈文案库
   4. 冬眠/唤醒/巡逻/等待等人格文案
5. 给“桌宠壳”和“功能面板”建立统一视觉过渡。

验收标准：

1. 任意两个弹层切换时，不再像两个独立子项目。
2. 用户能明显感知桌宠的性格，而不只是一个会动的青蛙图标。
3. 产品主色、按钮层级、卡片风格不再漂移。

### Phase D：在线增强与动画资产化（Week 6-8）

目标：
把在线能力和动画能力从“能跑”升级成“可扩展”。

交付项：

1. 登录链路重做
   1. 从技术流程改为用户流程
   2. 增加明确引导和状态提示
   3. 支持“先试玩后登录”
2. 旅行、通知、议会提醒做成真正的在线增强能力。
3. 建立动作状态机
   1. idle
   2. hover
   3. pet
   4. feed
   5. happy
   6. sleepy
   7. travel
   8. surprise
4. 把高频动作从零散 Framer Motion 配置收敛成统一动作资产。
5. 为未来接 AI Council / relationship-aware reminders 预留动画反馈口。

验收标准：

1. 登录后用户可以明确感知联机增益。
2. 高优先级动画不再依赖临时手写 keyframe 拼装。
3. 新增一个动作时，有清晰的资产接入路径。

## 七、执行级任务清单

## 7.1 P0 阻断项

这些项不解决，不建议继续做新功能堆叠：

1. 统一远端错误显示。
2. 明确离线试玩模式。
3. 去掉默认钱包伪装成“已接入”的感觉。
4. 梳理菜单优先级。
5. 为旅行、通知、我的青蛙建立统一数据状态组件。

## 7.2 P1 高优先项

1. 重做主界面信息层级。
2. 给互动、喂养、任务、旅行补完整反馈。
3. 收敛弹层尺寸和样式系统。
4. 建立桌宠文案语气库。
5. 补一个“首次使用引导”。

## 7.3 P2 增益项

1. 好友面板从展示卡升级为关系互动入口。
2. 家园与装饰系统强化成长期回流点。
3. 勋章、图鉴、记忆世界做成真正奖励反馈。
4. 链上监控从实验面板改造成可理解的事件提醒。

## 八、建议落地顺序

推荐按下面顺序推进：

1. 先修运行模式和异常态。
2. 再修主循环和菜单结构。
3. 再统一 UI 和交互反馈。
4. 最后升级登录、联机和动画资产管线。

不建议的顺序是：

1. 继续加新弹层。
2. 继续扩更多实验功能。
3. 在设计语言未统一前就批量补动画资产。

那样只会让桌面端越来越像“功能库”，而不是产品。

## 九、动画生成方案

## 9.1 现状判断

当前桌面端已经具备三种可用动画基础：

1. `Framer Motion`
   适合状态切换、轻量交互反馈、弹层动效。
2. `SVG 自绘 + Motion`
   适合桌宠主体动作，当前 `Frog.tsx` 已经在用。
3. `Lottie`
   工程已接入 `lottie-react`，但当前还是占位实现。

因此动画方案不应再新引入一套重框架，而应围绕这三层做生产管线。

## 9.2 推荐动画分层

建议把动画拆成 4 层：

### A. 核心角色动作层

用于青蛙本体：

1. idle
2. blink
3. pet-react
4. feed-react
5. sleepy
6. excited
7. sad
8. patrol
9. travel-ready

推荐实现：

1. 第一阶段继续用 `SVG + Framer Motion`
2. 把所有动作参数收敛到单独配置文件
3. 不再把动作散落在组件内部

适用原因：

1. 成本最低
2. 迭代最快
3. 与当前代码最兼容

### B. 情绪特效层

用于爱心、星星、汗滴、瞌睡泡、音符、惊叹号等反馈。

推荐实现：

1. `Framer Motion`
2. 小型 sprite 或 SVG 粒子

适用原因：

1. 不需要复杂资产
2. 很适合即时反馈
3. 性能风险低

### C. 高完成度演出层

用于孵化、升级、旅行归来、重大成就、冬眠唤醒等关键时刻。

推荐实现：

1. `Lottie JSON`
2. 动画文件放到独立 assets 目录
3. 通过事件触发演出播放

适用原因：

1. 演出质量明显高于纯代码补间
2. 便于设计和前端协作
3. 适合少量高价值场景

### D. 背景氛围层

用于天气、昼夜、家园氛围、轻漂浮粒子等。

推荐实现：

1. CSS + Framer Motion
2. 少量 SVG pattern / blur / gradient

适用原因：

1. 易控
2. 不依赖大体积资源
3. 能保证桌宠产品的轻量感

## 9.3 三种实际可执行的动画生成路线

### 方案一：设计主导型

流程：

1. 动效设计先出分镜和关键帧。
2. 用 After Effects 或同类工具导出 Lottie。
3. 前端接入 `lottie-react`。

适合：

1. 孵化
2. 升级
3. 稀有奖励
4. 旅行归来

优点：

1. 质量最高
2. 风格稳定
3. 适合品牌化演出

缺点：

1. 成本较高
2. 迭代速度慢于纯代码动画

### 方案二：前端参数化生成型

流程：

1. 定义动作 DSL 或配置对象。
2. 用统一 motion preset 生成不同情绪动作。
3. 让青蛙状态机按配置驱动动画。

适合：

1. idle
2. 呼吸
3. 眨眼
4. 摸头反应
5. 巡逻
6. 等待

优点：

1. 开发效率高
2. 维护简单
3. 非常适合频繁迭代

缺点：

1. 演出上限不如 Lottie
2. 需要先抽象出统一参数体系

### 方案三：AI 参考片段辅助型

流程：

1. 先用图像/视频生成模型产出“动作参考短片”。
2. 设计或前端按参考片段提炼关键 pose 和节奏。
3. 最终再落成 SVG motion 或 Lottie。

适合：

1. 探索新人格动作
2. 验证夸张风格
3. 快速寻找节奏参考

优点：

1. 早期探索快
2. 适合生成情绪参考
3. 有助于统一角色气质

缺点：

1. 不适合直接拿生成结果上生产
2. 一致性与版权要人工把关

结论：

**AI 更适合做“动效参考生成”，不适合直接做生产资产。**

## 9.4 推荐组合方案

对当前桌面端，最合适的是：

1. 高频动作：`SVG + Framer Motion`
2. 中频反馈：`Framer Motion + SVG 特效`
3. 低频高价值演出：`Lottie`
4. 新动作探索：`AI 参考片段 -> 人工定稿 -> 工程落地`

这是当前成本、质量、维护性三者最平衡的方案。

## 9.5 动画资产开发计划

建议按优先级做第一批 12 个动作：

1. idle 呼吸
2. 随机眨眼
3. 摸头开心
4. 喂食咀嚼
5. 困倦打哈欠
6. 睡眠泡泡
7. 被忽略委屈
8. 巡逻移动
9. 旅行出发准备
10. 旅行归来庆祝
11. 升级庆祝
12. 冬眠唤醒

每个动作都要定义：

1. 触发条件
2. 持续时间
3. 是否可打断
4. 是否叠加特效
5. 对应文案
6. 音效策略

## 十、最终建议

对桌面端，最重要的不是“继续堆更多功能”，而是完成一次产品收敛：

1. 先把离线可玩性和异常态修好。
2. 再把主循环和入口结构做清楚。
3. 再统一 UI 和桌宠人格。
4. 最后把动画资产化、联机能力产品化。

如果这个顺序执行对了，桌面端会从：

**一个功能多但有点散的 Demo**

升级成：

**一个真的有人愿意常驻桌面、愿意每天点几下、愿意回来养的桌宠产品。**
